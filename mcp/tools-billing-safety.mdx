JoggAI MCP exposes explicitly registered OpenAPI v2 operations as tools.
The exact scope-filtered list is returned by `tools/list`; clients should not
assume a fixed tool count. New REST endpoints do not become MCP tools automatically.
Legacy `/open` and `/open/v1` operations are not exposed.

## Tool groups

| Group | Examples | Typical scope |
| --- | --- | --- |
| Account | Account details and remaining quota | `account.read`, `quota.read` |
| Catalog | Avatars, voices, music, templates, and styles | `catalog.read` |
| Assets | Signed upload requests | `asset.write` |
| Scripts | Script submission and result lookup | `script.generate` |
| Voice | TTS and ASR submission and status | `voice.generate` |
| Avatars and images | Photo and product avatar generation | `image.generate`, `video.generate` |
| Video | Avatar, product, template, lip sync, and translation jobs | `video.generate` |
| Products | Product records, previews, and results | `product.read`, `product.write` |
| Webhooks | Event discovery and endpoint management | `webhook.read`, `webhook.write` |

Tool names and input JSON Schemas come from the JoggAI OpenAPI v2 contract. The
agent should use the schema returned by `tools/list` instead of inventing REST
paths or fields.

## Paid tools

Generation tools can consume the selected Space's existing JoggAI credits. There
is no separate MCP balance or MCP surcharge.

Every credit-consuming tool includes a billing warning in its description and is
marked with a destructive hint so compatible clients can request confirmation.
Examples include:

- Speech synthesis and transcription
- AI scripts and avatar images
- Avatar motion and lip sync
- Avatar, product, preview, and template video generation
- Video translation

<Warning>
An OAuth scope is permission to call a tool, not approval for a particular
charge. Review the tool name, billing warning, Space, duration, image count,
preview count, and other cost-driving inputs before confirming.
</Warning>

Read-only status tools do not resubmit work. When retrying after a timeout, query
the existing task ID before creating another paid task.

<Warning>
MCP transport retries are not a billing idempotency guarantee. If a paid submit
call times out before returning a task ID, do not replay it automatically. Some
tools accept an explicit idempotency key; otherwise inspect the matching list or
status tool, then contact support if the outcome is still unknown.
</Warning>

## Asynchronous jobs

Generation submissions normally return a task or resource ID. A robust agent
workflow is:

<Steps>
  <Step title="Review inputs and billing warning">
    Confirm the selected Space and cost-driving parameters before submission.
  </Step>
  <Step title="Submit once">
    Store the returned task, video, generation, or preview ID.
  </Step>
  <Step title="Poll the matching status tool">
    Continue until the job completes or returns a terminal failure.
  </Step>
  <Step title="Reuse the existing result">
    Do not create a duplicate because a client connection or polling request
    timed out.
  </Step>
</Steps>

## Uploads

MCP JSON-RPC requests do not carry large media files. An upload tool returns a
short-lived signed URL, method, and required headers. Upload the bytes directly
to object storage, then pass the resulting asset reference to another tool.

Treat signed URLs as credentials. Do not log, publish, or reuse an expired URL.

## Space and resource isolation

Authorization binds the session to a JoggAI user and selected Space. Private
avatars, images, products, generation tasks, and other resources must belong to
that authorized context. Knowing another resource ID does not grant access.

Team members use the Space's actual billing account for quota checks and paid
operations. If Space membership, ownership, or plan eligibility changes, an
existing token may stop authorizing calls.

## Webhooks and external effects

Creating, updating, or deleting webhook endpoints changes where JoggAI sends
events. Confirm the destination domain and selected endpoint before a write or
delete. Never send authorization headers, OAuth tokens, or signed asset URLs to a
webhook destination.
